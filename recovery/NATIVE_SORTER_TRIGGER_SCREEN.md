# Level 2 source-only decision: native-first Sorter triggering and movement

**Date:** 2026-11-14 (owner local date). **Authorized scope:** read-only official documentation plus **source-only tests** on the canonical **1.4.1** implementation. **No 1.5 inputs**, no server or LAB changes, no new scheduler implementation. **Decision:** disqualify native-only substitutes that cannot satisfy the existing Sorter contract; keep the remaining observation boundary **UNRESOLVED** pending adequate native evidence or an authorized BDS comparison.

Primary original source: [1.4.1 `processColumn` / `schedulerTick`](https://github.com/partom24/HartLogistics2/blob/0ea3000651c116b0fa1acc2836ab7e1bcfbc6269/addon/behavior_pack/scripts/main.js#L3380), [native Sorter JSON](https://github.com/partom24/HartLogistics2/blob/0ea3000651c116b0fa1acc2836ab7e1bcfbc6269/addon/behavior_pack/blocks/sorter.json), [Level 1 API families](../LEVEL1_NATIVE_API_RESEARCH_141.md), and [M01–M06/M17 decisions](../LEVEL1_MECHANISM_DECISIONS_141.md). Source-only test: [`level2_native_scheduler_screen.test.mjs`](tests/level2_native_scheduler_screen.test.mjs).

## 1. State the actual requirement

The input is a **native vanilla Hopper** above **one or more custom Sorter blocks**, in the owner's existing stacked layout. The original 1.4.1 code applies these semantics:

- A powered source Hopper or relevant powered Sorter prevents Hart's prohibited transfer; BYPASS must permit the original vanilla pass-through.
- Inspect the Hopper's *actual item* and select the destination in the order **specific Filter → destination-seeded Auto → Wildcard**, keeping the original **bottom-to-top** physical Sorter order within each priority. Other modes/empty filters do not accept.
- Honor live destination capacity, partial-stack preference, metadata-specific matching and safety/fault boundaries; do not silently change actual Hopper transport behavior.
- Intercept eligible cargo before native Hopper movement carries it past a matching Sorter under original conditions. Retaining native transport for unmatched cargo is required.
- Do not require the owner to add redstone components, alter existing storage geometry, empty Receivers or rewire stacked columns.

A native item-movement method that still requires scanning every eligible Hopper to discover an item is **not itself a native replacement for the trigger problem**.

## 3. Decisive source-only witnesses — counterexamples, not runtime claims

**Witness W1 — same comparator signal, different required Hart destinations.** The comparator reports normalized slot fullness. A single unit of a stackable stone item and a single unit of a stackable dirt item in otherwise empty five-slot Hoppers each produce the **same comparator signal strength 1**. But a Sorter column with a stone Filter and a seeded Auto route sends stone to **Filter** and dirt to **Auto**. Source-only tests execute original `processColumn` to confirm the distinct selections. Comparator power alone cannot supply the missing identity to a routing engine.

**Witness W2 — changed cargo without changed comparator power.** In the same five-slot Hopper, 20 stone units and 21 stone units both yield **signal 1** under the comparator fullness formula. Therefore a proposed event that fires **only on power-level change** cannot be a universal cargo-change trigger. A comparator might still be useful as a *coarse wake-up hint* in a **different, explicitly approved physical design**; it is not an exhaustive observer.

**Witness W3 — no custom block tick hook in original Sorter.** The original `sorter.json` uses `minecraft:redstone_consumer` and custom `hartlogistics:redstone_input` but has **neither `minecraft:inventory` nor `minecraft:tick`**. Source-only insertion of an `onTick` callback would still query the adjacent **vanilla Hopper** to learn its cargo. The absence of a custom inventory component in this original JSON does **not** prove such a block could never be engineered; it proves only that original Sorters do not contain one.

**Witness W4 — vanilla physical movement ≠ four-mode policy.** Original `processColumn` sorts candidate destinations by Filter, Auto, then Wildcard, rechecks before transfers, excludes BYPASS and respects power; original `rebuildTopology` sorts physical rows from bottom to top. The source-executed test uses the original function bodies and controlled mocks, not a rewritten scheduler.

These witnesses **disqualify specific naïve substitutes**. They do not measure native API cost, exhaust every possible future API or demonstrate that the old polling approach is optimal.

## 5. Next permissible decision (no new scheduler code yet)

**Do not optimize or replace `schedulerTick` merely because it is costly.** First establish the minimum reliable item-observation boundary **compatible with existing layout**, using actual 2.7 API declarations and a falsifiable plan for Hopper timing, loaded/unloaded state, stacked Filter→Auto→Wildcard priority and redstone lock. Measure native work per useful transfer *and* idle call volume only if actual BDS testing is subsequently authorized. Native Container movement can be examined separately from arrival detection, and no source-only mock is allowed to certify persistence or safety.

**Boundaries:** This document does **not** establish a fully native Sorter engine; does **not** require new comparator/observer blocks; does **not** authorize a world modification or testing in BDS; and does **not** justify restoring 1.5 implementation materials. The archived 1.5 branch remains isolated under the recovery mandate.

**Current verdict:** **No documented 2.7 native, no-layout-change *complete* replacement for Hart Sorter triggering and priority has been established.** Retain native vanilla movement as the default physical primitive, and leave the minimal custom **observation + Hart policy** requirement under explicit investigation, not automatic implementation.
