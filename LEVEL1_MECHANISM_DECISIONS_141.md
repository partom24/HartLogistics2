# LEVEL 1 — Decision matrix for all 40 original 1.4.1 custom mechanisms

**Evidence:** 1.4.1 source + official Microsoft/Mojang API documentation, **not** runtime proof, benchmark, or 1.5 source. **Version fence:** `@minecraft/server 2.7.0` and BP min engine `1.26.50`. **No new code design is authorized by these decisions.** Every N-ID points to [official API research](LEVEL1_NATIVE_API_RESEARCH_141.md); M-IDs match [the canonical 40-row mechanics table](NATIVE_FIRST_MECHANICS_AUDIT.md).

**Pinned 2.7 API and Level 2 native-custody follow-up:** [exact native signatures, 68 source-executed tests, 11 official-versioned type checks, and retained custom gaps](recovery/NATIVE_TRANSFER_AND_CUSTODY_LEVEL2_DECISIONS.md). None of these is a BDS-runtime test or authorization to implement a substitute.

**Post-Level-1 source-only decision on scheduling:** [Native Sorter trigger screening and comparator/event counterexamples](recovery/NATIVE_SORTER_TRIGGER_SCREEN.md), with [54 source-executed Level 2 cases](recovery/LEVEL2_SOURCE_EVIDENCE.md). This does not establish a native item-arrival callback or authorize a scheduler rewrite.

**Disposition terms:** `E` already native-integrated; `C` native partial/contract candidate; `G` Hart domain behavior has no documented complete native substitute; `U` crucial correctness or durability guarantee undocumented. `X` for invalid-version/incorrect alternative. **C means evaluate, NOT adopt.** Many rows contain a mix. Every row is Level 1 source/doc finding and its follow-up can be refused early if native is technically insufficient.

## 2. Documented-yes vs sufficient-for-Hart: make the distinction explicit

**Native already used in 1.4.1** is not "newly discovered": Hopper engine movement, inventory components, native item frames, redstone consumer callback, block permutations, native world dynamic properties, entitySpawn, player interactions, renderer assets, and the status custom-command registry. The review must focus on **unnecessary frequency and duplication** and on testing whether a stronger native method can safely replace manually implemented physical work.

**Native helper exists, but full subsystem replacement is not established**: `Container.firstItem/firstEmptySlot`, `contains/find`, `moveItem/transferItem/addItem`, `ItemStack.clone`, `World.setDynamicProperties`, entity inventory, `Entity.addItem`. Each makes a smaller operation possible; none documents all Hart routing, journal, FIFO, opaque-item, unload and transaction requirements.

**Documented invalid inference**: `onTick` or `runJob` is an inventory-change event; `playerInventoryItemChange` observes Hopper cargo; `blockContainerOpened` (2.8) fires on Hopper automation; `getParts` (2.9) is in baseline 2.7; `isStackableWith` can compare arbitrary nonstackable item identities; `emptySlotsCount=0` means no merge capacity; `setDynamicProperties` makes inventory+ledger crash-atomic; entity `private` proves nobody can mutate cargo; world property JSON can persist a raw ItemStack object.

**Version boundary:** Microsoft Learn's "stable" pages document newer releases and occasionally explicitly mark pre-release elements. All L2 work starts by checking the **exact 2.7.0 TypeScript definitions** and actual Bedrock server version—not by upgrading the pack merely to access a tempting API. API upgrade is a separate owner-controlled compatibility decision.

**Avoid 40 separate sessions.** These are grouped capability proofs. A single proof should cover all M-IDs that depend on a shared API. When a candidate fails the **documented** contract, do not build a prototype. No arbitrary unit rig or replacement owner world is required; actual BDS testing remains a distinct authorized stage.

## 4. Limits and scale — SOURCE vs PROPOSAL vs UNKNOWN

| Resource / operation | Verified original 1.4.1 | Level 1 interpretation | Required evidence before adopting a new threshold |
| --- | --- | --- | --- |
| Receiver ordinary Q4 capacity | **250,000 items** | Product compatibility requirement, not a native Container capacity | Counting, persistence and backpressure on existing populated Receiver(s) |
| Q4 page | **64 entries**, **30,000 char** page/entry guard | Source implementation bound, not official per-property byte ceiling | Exact 2.7 errors and storage bytes, including Unicode/metadata |
| Registry shards | **24,000 UTF-16 char** target | Compromise to avoid original dynamic-property single-key issue | Reads/writes and observed property size limits under nominated BDS |
| Sorter move budget | **16** per column, **256** global | Script budget, not engine throughput ceiling | Fairness/latency at owner scale and effects on native Hopper |
| Collector/Receiver batching | **16** each, **256** global | Script configured item-count budget | Backlog drain, FIFO and concurrent input/egress |

| Provisional timing targets | None validated in this recovery | Mandate suggests 19.5+ TPS and p95/p99 script targets; **targets, not official limits** | Paired 1.4.1 vs candidate profile with equivalent useful throughput |
| Container slot count | Hopper 5, chest typically 27/54 when proven alias | Native Container is a finite *slot* store; full does not imply unmergeable | Slot-accurate native transfer test, especially double chest |

## 5. Recursion and closure register

For every proposed replacement, link **(1) original function and M-ID, (2) N-ID and official API link, (3) exact baseline manifest support or 2.7 typing evidence, (4) which native step replaces which custom step, (5) what Hart-only policy remains, (6) expected change in per-tick native calls and bytes, (7) one test that could disprove it, (8) final measured result**. No M-ID is closed until all these fields are addressed; this Level 1 matrix establishes (1), (2), and a source/documentary portion of (3)–(7), **not** (8).

**Level 1 conclusion:** Every one of the **40 baseline custom-mechanic groups** has now been mapped to documented native capabilities and their limits. This does **not** mean any particular fraction is replaceable or that BDS performance has improved. The high-leverage unknowns are generic Hopper observation, physical move/custody durability, metadata-rich item persistence, and the real cost of recurring world/registry scans.
