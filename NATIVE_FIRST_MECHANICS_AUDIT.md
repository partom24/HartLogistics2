# Native-first audit of Hart Logistics **1.4.1** — custom mechanics, alternatives, limits and scale

**Scope and provenance:** This is a **source audit of the exact 1.4.1 import** `0ea3000651c116b0fa1acc2836ab7e1bcfbc6269`, its `addon/` tree and `BASELINE_HASHES.json`. It uses current *official Microsoft Bedrock stable API documentation* only as **candidate capability evidence**, NOT 1.5 code, design, benchmarks or results. No 1.5 material is permitted as an implementation input. No candidate has been tested in BDS for this recovery. **Date:** 2026-11-14.

**Source anchor:** [immutable baseline `main.js`](https://github.com/partom24/HartLogistics2/blob/0ea3000651c116b0fa1acc2836ab7e1bcfbc6269/addon/behavior_pack/scripts/main.js). Function-by-function and every-file accounting: [recursive census](BASELINE_141_RECURSIVE_CENSUS.md). **Level 1:** [39 official native API capability families with signatures/version restrictions](LEVEL1_NATIVE_API_RESEARCH_141.md) and [all 40 M-ID decisions, scaling caveats and disqualifying tests](LEVEL1_MECHANISM_DECISIONS_141.md). Binding stages: [recovery mandate](RECOVERY_MANDATE.md).

**Units for scale:** `S` = registered Sorters, `C` = contiguous stacked Sorter columns, `H` = Sorters per relevant column, `I` = Hopper/input slots, `D` = destination slots, `K` = Collectors, `R` = Receivers, `Q` = queue entries, `P` = queue pages, `E` = filter-display entities, `L` = connected route length. `O(...)` describes source-code work tendencies, **not measured Bedrock runtime**, and conservative upper-bound notation may overstate common cases. `E/F` = events or frequency. **ALL proposed limits below are test gates, not hard build restrictions.**

| Receiver virtual capacity | `QUEUE_CAPACITY=250,000` items per Receiver | Preserve exact 250,000 for existing Receivers; exercise ≥200,000 queued + multiple linked Receiver paths | No truncation, empty-before-upgrade or automatic metadata conversion |

| Registry strings | Baseline comment notes a 32,767-character string limit; two generations, 24k target | Maintain **24k source shard target** until platform validation; compare native property byte usage via API | Fail closed before writes that exceed engine limits |
| Sorter transfer budget | `PER_COLUMN_BATCH=16`, `GLOBAL_MOVE_BUDGET=256` (item counts, not chunks/blocks) | Profile and tune without changing accepted routing order; target throughput **greater than matched 1.4.1** | Budget can hide overload by starving columns |
| Collector ingress / Receiver output | `COLLECTOR_BATCH=16`, `RECEIVER_BATCH=16`, `LOGISTICS_GLOBAL_BUDGET=256` | Preserve fairness; test sustained output, backpressure and backlog drain across multiple active Receivers | No false success when output Hopper full/locked |

| Scheduled route checks | `schedulerTick` and `logisticsTick` /1 tick | Goal: idle columns cause **0 destination inventory reads and 0 journal writes**; no missed next-eligible-tick cargo | Do not claim generic Hopper-change event exists |
| Script timing | No baseline measured timings in this recovery source census | **Engineering target to validate:** HL-specific work p95 ≤10ms, p99 ≤25ms; idle p95 ≤5ms on agreed hardware, plus **server ≥19.5 TPS** during representative load | These are proposed goals, not Bedrock API limits or demonstrated outcomes; capture independent engine metrics |

## C. Verified native API candidates, source URLs and uncertainty

- [Container stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/container?view=minecraft-bedrock-stable): `emptySlotsCount`, `size`, `firstEmptySlot`, `getItem`, `addItem`, `moveItem`, `transferItem`. **Do not infer durable atomic commit** from the documented move method.
- [ItemStack stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/itemstack?view=minecraft-bedrock-stable): `clone` documents exact copy including custom data/properties, `isStackableWith` checks custom data. This does not establish native persistence for a new custom block without BDS proof.
- [System stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/system?view=minecraft-bedrock-stable): `run`, `runInterval`, `runJob`. The last is a time-sliced generator, **not** an event that fires on Hopper inventory changes.
- [World after-events stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/worldafterevents?view=minecraft-bedrock-stable): player block placement/break/interact, `entitySpawn`, piston event and **player** inventory changes. **No general Hopper inventory-change event is established by this documentation.**
- [BlockCustomComponent stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/blockcustomcomponent?view=minecraft-bedrock-stable): `onTick`, `onRedstoneUpdate`, `onPlayerInteract`. Verify custom block components / manifest version and exact redstone gate.
- [Block stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/block?view=minecraft-bedrock-stable): `getRedstonePower`, `getComponent`, `setPermutation` and loaded-block restrictions.
- [World stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/world?view=minecraft-bedrock-stable): world dynamic properties, IDs and total byte count. **No documented multi-property crash atomicity**.
- [EntityInventoryComponent stable](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entityinventorycomponent?view=minecraft-bedrock-stable): entity-native inventory and siphon/drop properties; **not automatic evidence of owner-secure, always-loaded, crash-safe physical custody**.

### Required proof questions, not assumptions

1. Does the stable target API expose *any* reliable generic inventory-change signal for Hopper or container contents on BDS without experiments? If not, determine the least-cost correct observation boundary rather than propose an imaginary event.
2. Can a custom block or entity persist an original opaque `ItemStack` through restart, unload, other addons, Hopper interactions, and unexpected termination, while preventing double ownership? Test before selecting a new carrier.
3. Do `transferItem`/`moveItem` preserve every relevant identity, partial merge/slot priority and safe crash recovery? Native convenience ≠ proof of transaction durability.
4. Can Bedrock native redstone, item-frame and UI events eliminate polling without stale cached block state?
5. How does total native API work grow with S, C, D, R, number of items and connected banks? Detect **O(S) per idle tick**, **O(D·H) repeated scans**, **O(E) global sweeps**, and Q4 write amplification using actual instrumentation.

**Engineering instruction:** Every M-ID must receive an explicit verdict `NATIVE SUFFICIENT`, `MINIMAL CUSTOM REQUIRED`, or `UNVERIFIED / HOLD` after API and Bedrock feasibility evidence; the entries above are a **complete baseline custom-mechanic candidate inventory**, not a conclusion that any substitute works.
