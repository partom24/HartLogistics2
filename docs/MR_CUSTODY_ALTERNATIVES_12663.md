# Native metadata-rich ItemStack custody — safe options on BDS 1.26.63.1

**Date:** 2026-11-07. **Status:** DESIGN OPTIONS ONLY; no implementation or LAB deployment approved. **Existing 1.4.1 source and saved worlds must remain unchanged until a separately approved change.** [PG-03 results](BUNDLE1_PREPARATION_RESULTS.md) document the runtime blocker. This memo examines *possible* lossless alternatives, not proofs of them.

## Confirmed platform boundary

- At **1.26.50**, the **container field** on a custom block's `minecraft:block_entity` was specifically experimental, even though the component itself was stable. Microsoft [1.26.50 creator notes](https://learn.microsoft.com/en-us/minecraft/creator/documents/update1.26.50?view=minecraft-bedrock-stable).
- Only **26.70.23 Beta/Preview (November 3, 2026)** says that this `container` field was released from experimental for custom blocks. This is **a preview**, not proof it is present in the owner's **stable BDS 1.26.63.1**. [Minecraft 26.70.23 Preview notes](https://feedback.minecraft.net/hc/en-us/articles/50103892132365-Minecraft-Beta-Preview-26-70-23).
- Owner's LAB screenshots after verified source installation show `hlprobe:mr_container` missing from Creative and rejected by `/give`. That establishes lack of a usable test block in this session; it does not independently reveal every BDS pack-loader error. **PG-03 NO-GO** for current no-experiments requirement; PG-04 and PG-05 **BLOCKED**, never claimed to have exercised MR transfer/persistence.
- Microsoft's [stable `Container` API](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/container?view=minecraft-bedrock-stable) documents `moveItem` / `transferItem` for actual native block and entity inventories. Its [entity inventory](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entityinventorycomponent?view=minecraft-bedrock-stable) and [entity component](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/entityreference/examples/entitycomponents/minecraftcomponent_inventory?view=minecraft-bedrock-stable) references document a native inventory model. **Availability on a documentation page is not substitute evidence of the complete candidate on BDS 1.26.63.1.**

## Hard acceptance requirements for any alternative

1. **Ownership invariant:** every accepted MR ItemStack has exactly one durable custodian at every point: an actual native slot or original source. A journal/index is **metadata only**, never a second authoritative copy. No acknowledgment or capacity reservation before durable custody is verified.
2. **Full metadata:** do not approximate native stacks with `typeId`/amount/name/lore JSON. Test relevant metadata *classes* (names/lore, enchantments/durability, custom components or add-on items as available), but don't demand repeating arbitrary equivalent item IDs.
3. **Finite capacity and backpressure:** blocked/invalid/unloaded/untrusted backing inventory means **do not remove from source**. Native MR space is not interchangeable with ordinary Q5 250,000-count quota or 200,000-item Bulk Storage accounting.
4. **Unloaded regions and crash recovery:** never infer “empty”, “full” or “transfer succeeded” from an unavailable container/entity. Build a monotonic custody token/epoch and idempotent source-to-destination acknowledgement. Prove power interruption at each critical step, restart and later chunk load; no duplicated native carrier.
5. **World upgrade compatibility:** existing placed 1.4.1 Sorter/Collector/Receiver IDs, coordinates, links, q2/q3/q4 states, q4 journal and direct-only MR bypass still work without manually emptying/replacing blocks. Merely adding a carrier to a fresh world does not prove migration safety.
6. **Vanilla Hoppers do not pause:** a global *Hart script* routing freeze cannot stop vanilla Hopper movement. Any carrier approach must isolate Hopper access and prevent concurrent vanilla transfers during ownership transitions.
7. **Physical footprint & cleanup:** preserve the owner’s existing production-derived LAB clone and protected production world. No hidden placement of chests/entities into valuable structures. Any temporary carrier lease/rig must be removed immediately after testing, but **not while it holds an item**.
8. **Menus and existing interactions:** no interference with Collector Link/Relink, Receiver confirmation, sneak-place Hopper, redstone modes, or inventory UI. Avoid requiring experiments or cheats; no external native bridge via HartBots production.

## Suggested decision order (future approval required)

**First:** leave MR routing **on the original 1.4.1 direct-only lossless path**, no new persistent MR queue, while considering separately approved work that has no MR custody dependency.

**Second:** compare a *guarded vanilla backing-container* concept against a *documented custom inventory entity* purely on paper and through **offline simulations** (no world writes). The block approach is more straightforward but requires a visible/declared physical location and space; the entity approach has much more complex identity and lifecycle risk. If neither can satisfy zero-loss and saved-world constraints, reject both.

**Third:** wait for a published stable release supporting native custom-block containers, then ask whether updating the server/client minimum is an acceptable compatibility decision. Do **not** deploy a Preview as a disguised prerequisite. Even on a supported version, verify *old placed blocks* and their persisted state, not just newly placed blocks.

**Minimum targeted future test gates:** (i) 1.26.63 no-experiment carrier available with native slots; (ii) exact ItemStack fidelity and deliberate blocked destination; (iii) restart/unload/custody and break/removal semantics including one injected failure; (iv) 1.4.1 placed-block upgrade with linked networks and journal intact. Automated checks can run without an arbitrary count cap; group only **owner-performed BDS checks** in 2–3 related operations per fully READY rig. All future probe/source changes need their own bounded authorization.

**Current decision:** **No alternative has GO**. The only accepted preservation behavior is the existing 1.4.1 path. Do not replace it until a proposed architecture proves both stable API and no-loss custody.
