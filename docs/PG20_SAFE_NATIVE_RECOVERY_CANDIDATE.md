## Fixed and preserved contracts

- [PG-19](PG19_LEGACY_MR_RECOVERY_HAZARD.md) demonstrated that the original `safeMovePartial` can debit a live native metadata-rich item from source while its in-flight journal only contains a filtered item reconstruction. `recoverJournal` on the old post-debit/pre-credit exception path recreated an ItemStack without Adventure restrictions/keep-on-death/lock-mode and cleared the journal under a controlled Node fake-container failure. The original 1.4.1 bytes are still preserved at `addon/`; this hazard was not observed as live BDS disk corruption.
- The [PG-20 guarded builder](../candidates/pg20/prepare_candidate.py) reconstructs **original 1.4.1 + owner-accepted PG08 UI**, then applies a minimal exact-source-anchor patch and [native-MR helper](../candidates/pg20/native_recovery_overlay.js). **No extra runtime content** from the finished PG13 shadow, PG14 chest custody, PG15 cut commands remains. Their offline test suites and historical evidence stay in Git. The 72 source hashes, UUIDs, Q4 schema, Sorter modes, filter/UI, Hopper and Dropper/Dispenser paths, redstone gates and item queues are untouched outside the explicitly described physical recovery changes.
- Only the original **direct-only, Q4-unsafe Collector Hopper → loaded Receiver output Hopper** call chooses a new native path. That path requires known source and destination, **whole ItemStack only**, destination slot currently **empty**, same dimension, no prior physical journal, readable exposed metadata and suitable destination room. It writes a single old-key intent marker with `opaqueTag:"pg20-native-opaque-v1"` and item-type/count/location, but **not a reconstructable item definition**. It then performs **one native `src.moveItem(srcSlot,dstSlot,dst)`**, reads both slots and compares all *inspectable* original item attributes, and only after clean synchronous success clears the marker.
- An interrupted opaque marker is always **HOLD/no replay/no clear/no reconstruction**, even if source and target readback look correct. Every subsequent `safeMovePartial` route, including ordinary Sorter source→storage, refuses new source debits while an existing physical marker is present. Unknown/corrupt marker values are never interpreted as absent.
- For an **old legacy journal** loaded during upgrade, the previously unsafe **post-debit/pre-credit reconstruction** and **post-credit/pre-debit auto-debit** branches now HOLD rather than infer identity and mutate. Untouched prepared and already completed legacy transactions still use their old no-physical-write marker cleanup logic. The untouched and completed readbacks are **not** proof of exclusive external-writer control or crash-atomicity; they retain baseline semantics.
- Whole-stack native `Container.moveItem` is documented by Minecraft's stable Script API as a native operation, and PG14 had previously exercised it on **ordinary single chests** in LAB. That does **not** prove a disk-level atomic world-property+inventory commit, a live Hopper-to-Hopper MR handoff, or any hard-crash outcome.

## Deliberately different behavior and open risks

1. **Safety versus liveness:** If an old partial journal is encountered, the previous 1.4.1 automatic resume is no longer attempted, **including for ordinary items**. All new physical journal writes HOLD while it remains. This is a material behavior change requiring owner evaluation: the network may pause pending an exact forensic/manual decision, but an ambiguous MR item will not be fabricated or irreversibly debited by recovery. There is not yet a validated automatic settlement/repair policy.
2. **Full-stack/empty-slot only:** Unlike the old two-`setItem` direct-only path, native MR fallback does **not** split partial Q4-unsafe stacks or merge an occupied output slot. Those cases remain at source rather than risk flattening; they are known compatibility/throughput limits. The usual nonstackable enchanted book or named tool is a complete one-item stack and still fits this route; not all possible 1.4.1 metadata item classes have yet been accepted on BDS.
3. **What is proven:** 25 synthetic Node tests execute the **compiled candidate's actual move and recovery functions** under mock inventory/world exceptions; 6 Python build invariants and 13 synthetically guarded Windows LAB install/rollback cases plus a Windows PowerShell launcher Plan fixture passed CI (see below). Tests cover exact native metadata in the mock, no serialization, held journal after injected before/after failure, write/readback mismatch, legacy non-reconstruction, ordinary happy-path compatibility and blocked source debits.
4. **What is NOT proven:** Same-tick observations are not unique durable item identifiers or an authenticated physical receipt. Unrelated scripts/players/vanilla Hoppers remain external writers; a simultaneous foreign Hopper/player action or an abrupt BDS kill may result in states that cannot be automatically reconciled. `pg20InspectableNativeFingerprint` covers exposed accessible metadata, not arbitrary third-party opaque components. No claim of power-loss atomicity, no new Q5 persistent MR slots, no spendable Bulk, no custom experimental storage, no production release.
5. **Existing LAB diagnostic cleanup:** PG15/PG14 test markers were owner-observed clear, **but PG13 `shadowclear` remains unverified in prior records**. The exact ready test card requires the owner to execute `/hartlogistics:shadowclear` under the **still-installed PG15** pack before replacing it; otherwise removing completed PG13 runtime commands could strand the old two test-owned keys. No other world dynamic property is cleared automatically.
